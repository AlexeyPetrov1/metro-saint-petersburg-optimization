Общий контекст
Вы разрабатываете один модуль репозитория четвёртого участника хакатона по первой линии метро Санкт-Петербурга. Человек 2 владеет данными и прогнозом, человек 3 — общими схемами, распределением поездок, симулятором и экраном, человек 4 — решениями и экономикой. Не создавайте их компоненты заново.
Сначала прочитайте актуальные AGENTS.md и README репозитория, общий контракт и приложенный план. Имена функций ниже — предложение интерфейса; согласованные схемы репозитория имеют приоритет по форме, но противоречия в смысле нужно явно зафиксировать.
Подтверждено для кейса: 113 секунд минимального интервала, 8 вагонов, норма 120 человек на вагон, максимум 53 состава именно на линии, два депо. 99 минут оборота — ориентир источника. Резерв 4 состава в файле назван идеальным, фактическая доступность неизвестна. Времена 7/30 минут из переписки и 15–20 минут из файла имеют конфликтующую семантику: не складывать или выбирать их молча.
120 суток 15-минутных входов — основной реальный спрос; это не моментная численность и не готовая загрузка поездов. OD, пересадки и распределение по вагонам требуют сценариев. Денежные ставки не заданы. Нельзя выдавать учебные коэффициенты за рублёвую экономию.
После фиксации схем работайте только в своей области файлов. Общие схемы меняет координатор с человеком 3, CLI и зависимости — работа E. Данные API не нужны для автономной реализации. Заглушки разрешены для программных проверок и обязаны иметь evaluation_mode=fixture.
Ограничения физики нельзя компенсировать штрафом. Unknown не равен passed. Все планы сравниваются на одном спросе и начальном состоянии. Очереди и обязательства не исчезают в конце 120 минут. Сохраняйте источники и версии; не применяйте реальные команды к системам метро.
Минимум инфраструктуры: Python-пакет, чистые функции, JSON/Parquet и pytest. Не добавляйте сервер или LLM без необходимости. Пройдите значимые проверки своей функциональности, передайте точные команды запуска и ограничения. Не утверждайте, что интеграционные проверки выполнены, если использовали заглушку.

GOAL 15 Работа C Движок выбора

Цель: выбрать лучший полностью проверенный вариант из небольшого определённого набора. Собственные файлы: candidates.py, selector.py, policy_state.py. Входы: снимок, прогнозные сценарии, правила, ставки, интерфейсы A/B и оценщик человека 3.

Порядок действий

- Сначала написать селектор на таблице заранее известных Evaluation. Доказать порядок приоритетов: физическая допустимость → обслуживание → расходы → устойчивый порядок равенства.

- Генерировать KEEP_PLAN, один доступный резерв по каждой допустимой точке, продление одного снимаемого состава, снятие одного достижимого состава. Времена брать из разрешённых окон, не только из 15-минутной сетки.

- Разворачивать через expand_action; удалять одинаковые планы; оценивать все обязательные сценарии с одинаковыми исходными условиями.

- Вести счётчики уникальных моментов расчёта, минимальную длительность режима и уже принятые обязательства. Не отменять усиление только потому, что оно само снизило загрузку.

- Возвращать no_change, recommended, conditional, insufficient_data, capacity_limit, no_feasible_candidate, alternatives_require_policy, evaluation_timeout или search_incomplete с причинами.

- Сохранять множество поиска, число оценённых вариантов, время расчёта, причины отсечения и выбранную версию сценария. Начальный бюджет 5 секунд — инженерная настройка, измерить её на машине команды.

Контрольные примеры

Самый дешёвый вариант нарушает интервал — исключён при любой цене. Дешёвый вариант оставляет недопустимую очередь — исключён. Все кандидаты плохи — нет ложного recommended. Перестановка списка не меняет ответ. Повтор request_id не запускает резерв снова. Истечение срока предложения и конфликт состояния приводят к перепроверке, а не к применению старого решения.

При тайм-ауте разрешён только полностью проверенный ранее найденный вариант со статусом search_incomplete; незавершённый кандидат не возвращается. Если нет проверенных альтернатив, честно сообщить об отсутствии результата. При неизвестных ценах несравнимые ресурсы не ранжировать выдуманными весами.

Критерий готовности

На маленьком пространстве селектор совпадает с независимым полным перебором. Через настоящий симулятор воспроизводятся ввод, отложенное снятие и уборка. Лучший среди кандидатов не называется глобально оптимальным расписанием. Продление поиска не должно менять уже завершённые оценки из-за мутации состояния.
